# tech-qa 11 · AI 质量：结构化输出、降级与评估 高频问答

> 落点：`common/ai/StructuredOutputInvoker`、`common/config/StructuredOutputProperties`、`common/evaluation/`（`UnifiedEvaluationService`、`EvaluationReport`、`QaRecord`）、`prompts/interview-evaluation-*.st`。

---

### LLM 输出的 JSON 不可靠，工程上怎么兜住？

**答：** 四层，从便宜到贵：

1. **Prompt 约束**：明确「只输出 JSON、不要解释、不要代码块」，并附 schema；
2. **本地修复**：常见小错（未转义引号、多余代码块围栏）先尝试机械修复；
3. **带错误重试**：把解析错误信息回喂给模型，让它自己改；
4. **降级兜底**：彻底失败时给规则结果或明确失败状态，绝不 500。

关键是**别把这套逻辑复制到每个业务里**——它应该是一个公共入口。

**本仓库：** 统一走 `StructuredOutputInvoker.invoke(...)`，`AGENTS.md` 里明确禁止业务代码自己复制重试逻辑。

---

### `StructuredOutputInvoker` 具体怎么做的？

**答：** 一个 for 循环 + 逐次加固的 system prompt：

```text
securedSystemPrompt = 原 system + 防注入指令 + 输出格式说明
for attempt in 1..maxAttempts:
    attempt == 1 ? 用原 prompt
                 : 用「重试 prompt」= 原 prompt + 严格 JSON 指令 + 「上次输出解析失败」+（可选）截断后的上次错误
    成功 → 记指标 → 返回
    失败 → 记 attempt 失败指标 → 记录 lastError
全部失败 → 抛 BusinessException(errorCode, 前缀 + 最后一次错误)
```

可配项（前缀 `app.ai`）：

| 配置 | 默认 | 作用 |
|------|------|------|
| `structured-max-attempts` | 2 | 最大尝试次数 |
| `structured-include-last-error` | true | 是否把上次错误回喂 |
| `structured-retry-use-repair-prompt` | true | 是否用修复型重试 prompt |
| `structured-retry-append-strict-json-instruction` | true | 追加严格 JSON 指令 |
| `structured-error-message-max-length` | 200 | 错误信息截断长度 |
| `structured-schema-validation-enabled` | true | 走 schema 校验解析 |
| `structured-metrics-enabled` | true | 埋点开关 |

另有 `convertWithRepair` 做本地引号修复；解析走 `BeanOutputConverter`，开校验时用 `.entity(converter, spec -> spec.validateSchema())`。

### 为什么把错误信息回喂给模型，而不是纯用正则修复？

**答：** 两者互补，但优先级不同。正则/机械修复只能处理**已知的、格式层面**的错误（引号、围栏），遇到「少了一个必填字段」「枚举值写错」就无能为力。把校验错误回喂给模型，等于让它做一次**语义层面的自我纠正**，覆盖面大得多。代价是多一次调用的时间和费用——所以最大尝试次数要小（这里默认 2），不能无限重试。

---

### 降级兜底怎么设计才算合格？

**答：** 三条判断标准：**用户看到的是可用结果还是明确失败**、**失败可不可重试**、**降级结果会不会被误认为正常结果**。

**本仓库三种降级形态：**

| 场景 | 降级 |
|------|------|
| 出题失败 | `generateFallbackQuestions` 给一批兜底题，功能不中断 |
| 评估 LLM 不可用 | 规则打分给出基础评价 |
| 语音会话无有效对话 | 生成一份 0 分空报告，保证前端结构完整 |
| 异步任务彻底失败 | 状态置 `FAILED` + 错误文案 + 提供重试入口 |

注意 `StructuredOutputInvoker` **自己不降级**——它只负责抛出带错误码的异常，降不降级由调用方按业务决定。这个分层很重要：公共组件不该替业务做产品决策。

### 评估为什么要分批？

**答：** 上下文窗口有限，题目一多会截断，导致后面的问答根本没被评到（而且不报错，静默变差）。分批把「一次评 20 题」变成「4 批各 5 题」，每批独立结构化输出。

**本仓库：** `UnifiedEvaluationService` 按 token 估算自动分批，每批走 `interview-evaluation-system/user.st`。

---

### 分批之后为什么还要二次汇总？

**答：** 因为**分批会带来评分尺度漂移**：前一批宽松、后一批严格，直接平均会失真。二次汇总把各批结果再交给模型做一次校准与总结（`interview-evaluation-summary-*.st`），输出统一的总分、优劣势与建议。

这是「分而治之」的通用代价：切分带来一致性问题，需要一个合并阶段来收敛。

---

### 评估维度怎么设计？

**答：** 维度要**可解释、可对比、和产品目标对齐**，并且给出上限分值便于聚合。

**本仓库：**

| 场景 | 维度 |
|------|------|
| 问答评估 | 知识点覆盖度、回答准确性、表达清晰度、深度与广度 |
| 简历评分 | 内容 25 / 结构 20 / 技能匹配 25 / 表达 15 / 项目 15 = 100 |

文字与语音共用同一套 `QaRecord` 输入与 `EvaluationReport` 输出，**目的就是让两种形态的结果可直接对比**；差别在于语音多一步 ASR 转写，转写错误会污染评估——这点在解读语音评分时必须记住。

### 结构化输出的质量怎么观测？

**答：** 至少三个信号：**成功率**（invocations 里 failure 占比）、**平均尝试次数**（attempts / invocations > 1 说明一次成功率低）、**延迟分布**（重试会显著拉高 P99）。

**本仓库：** 三个指标都有（`app.ai.structured_output.*`），但 `context` 标签因中文被规整成 `unknown`，**当前无法按场景切分**——先修标签再谈调优（见 [tech-qa/10](10-observability-rate-limit.md)）。

### 离线评测好、线上变差，常见原因是什么？

**答：** 四类 Gap：

1. **数据分布**：评测集是精选样本，线上有脏输入、超长文本、跑题提问；
2. **上下文差异**：线上有历史对话、多知识库混检、被截断的上下文；
3. **指标错位**：离线看格式正确率，用户在意的是「有没有帮到我」；
4. **系统因素**：并发下超时、限流、降级触发，评测时都没发生。

缩小办法：评测集从**线上真实样本**采样、把降级/超时算作失败计入指标、加线上反馈信号（点赞/点踩/重问率）。

### 怎么给这个项目建评测？

**答：** ⚠️ 项目未覆盖，这是我最想补的一块。我打算的最小可行方案：

1. **攒集**：30–50 条真实用例（简历 + 期望要点、RAG 问题 + 期望依据片段）；
2. **定指标**：RAG 看命中率与忠实度；评分看维度分方向是否合理、同一输入的稳定性（跑 3 次看方差）；
3. **打分**：规则能判的用规则（JSON 合法性、必填字段、分数范围），主观项用 LLM-as-judge，给固定评分标准；
4. **接流程**：作为一个可手动触发的任务跑，输出对比报告；调 Prompt / 换模型 / 改分块时看**相对变化**；
5. **收线上反馈**：给回答加「有帮助 / 没帮助」，逐步把评测集换成真实分布。

先做 1–3 就已经能挡住「改了 Prompt 结果变差却没人发现」这类问题。

### 什么该交给 LLM，什么该用规则？

**答：** 我的判断线：

| 交给规则 | 交给 LLM |
|----------|----------|
| 格式校验、字段必填、范围检查 | 语义理解、自然语言生成 |
| 分数聚合、加权计算 | 定性判断、给建议 |
| 去重、限流、状态流转 | 开放式抽取（简历/JD/邀约文本） |
| 可穷举的分类 | 长尾、模糊的分类 |

**能用规则做的就别用模型**——规则确定、免费、可测试。反过来，模型输出的结果要**用规则校验**（分数是否越界、必填是否齐全），这是最便宜的一道质量闸门。

## 我的口述清单

1. 结构化输出四层：Prompt 约束 → 本地修复 → 带错误重试 → 业务降级。
2. 重试上限要小（默认 2），把校验错误回喂比正则修复覆盖面大。
3. 公共组件只抛异常，降级决策留给业务——分层要干净。
4. 分批解决 token 上限，二次汇总解决尺度漂移。
5. 文字与语音共用输入/输出模型，是为了结果可对比。
6. 没有评测集就没有「效果变好了」的证据——这是我明确承认的缺口。

# tech-qa 06 · RAG 高频问答

> 落点：`modules/knowledgebase/`（`KnowledgeBaseVectorService`、`KnowledgeBaseQueryService`、`VectorRepository`、`RagChatSessionService`）、`prompts/knowledgebase-query-*.st`、`application.yml` 的 `spring.ai.vectorstore.pgvector.*`。  
> 模块视角见 [modules/04 知识库与 RAG](../modules/04-knowledgebase.md)。

---

### RAG 是什么？主流程有哪几步？

**答：** 检索增强生成——把外部资料检索出来塞进上下文，让模型基于资料回答。两条线：

```text
离线（写侧）：文档 → 解析 → 清洗 → 分块 → Embedding → 向量库
在线（读侧）：问题 →（改写）→ Embedding → 检索 TopK → 拼上下文 → LLM 生成
```

价值是：知识可更新、来源可追溯、成本远低于训练。

**本仓库：** 写侧是 Tika 解析 + 切块 + Embedding + pgvector；读侧是（多轮时先改写）→ 检索 → `knowledgebase-query-*.st` → 流式生成。

---

### 什么时候用 RAG，什么时候该微调？

**答：**

| 需求 | 选择 |
|------|------|
| 知识经常变、要引用来源 | RAG |
| 要改变**风格/格式/领域语感** | 微调 |
| 私有知识很多但预算有限 | RAG 优先 |
| 想压缩 Prompt 长度、降低推理成本 | 微调可能有帮助 |

实务上先 RAG，把「检索不到」和「答不好」分开定位后，再考虑要不要微调；两者也可以叠加。

**本仓库：** 纯 RAG，无微调。

---

### 文档解析和清洗要注意什么？

**答：** 多格式统一走解析器抽正文（PDF/Word/Markdown/TXT），要处理：页眉页脚重复、目录噪声、表格错行、控制字符、异常空白。噪声会**同时污染 Embedding 和上下文**，是 RAG 效果最容易被低估的一环。扫描件需要 OCR，OCR 噪声要额外后处理。

**本仓库：** Tika `BodyContentHandler` + `TextCleaningService`（去控制字符、压缩空白、修断行）；Markdown 有扩展名兜底判定；正文上限 5MB。

---

### 为什么要分块？chunk_size 和 overlap 怎么定？

**答：** 分块是为了让「检索粒度」既能命中细节，又不至于把无关内容一起塞进上下文。

- 块太大：向量语义被稀释、上下文浪费、易带入噪声；
- 块太小：语义被切断、需要更大 TopK 才能凑齐信息。

经验区间：中文技术文档 300–800 字/块、overlap 10–20%，并**尽量按语义边界切**（标题、段落）而不是硬切字符数。真正的定法是拿自己的问题集试。

**本仓库：** 由 Spring AI 的切分链路完成；⚠️ 目前没有针对本项目文档做过参数对比实验，属于要补的调优工作。

---

### Embedding 是什么？维度越高越好吗？

**答：** Embedding 把文本映射成向量，语义相近则距离相近。维度不是越高越好：更高维通常表达力更强，但存储、内存、检索开销都上升，边际收益递减。选型要看**目标语言/领域效果**、维度、成本，以及是否支持长文本输入。

**关键约束：** 换模型 = 向量全部失效，必须整库重建。

**本仓库：** 维度固定 1024，与 Provider 表的 `embedding_model` 配置对齐。

---

### 为什么选 pgvector，而不是 Milvus / Pinecone / Chroma？

**答：**

| 方案 | 取舍 |
|------|------|
| **pgvector** | 复用已有 PostgreSQL，事务/备份/运维一套，中小规模足够；超大规模与高级索引能力有限 |
| Milvus | 专业向量库，规模与索引丰富；多一套集群运维 |
| Pinecone | 托管省心；成本与数据出境要考虑 |
| Chroma | 轻量适合原型；生产能力弱 |

本项目本来就有 PostgreSQL，向量量级也不大，pgvector 是「少一个组件」的选择。

**本仓库：** `pgvector/pgvector:pg16` 镜像，`initialize-schema: true` 自动建 `vector_store` 表，索引类型 HNSW。

---

### HNSW、IVF 是什么？距离度量怎么选？

**答：** 精确检索是 O(N)，所以用近似最近邻（ANN）索引换速度：

- **HNSW**：多层图结构，查询快、召回高、内存占用大、构建慢；
- **IVF**：先聚类分桶再桶内搜索，内存友好、需要训练、召回受聚类质量影响。

距离度量要**和 Embedding 模型的训练方式一致**：多数文本模型输出归一化向量，用余弦（COSINE）最稳；归一化后余弦与点积等价，欧氏距离在未归一化时含义不同。

**本仓库：** HNSW + COSINE。

---

### TopK 怎么定？要不要设相似度阈值？

**答：** K 太小漏召回，太大引入噪声还烧 token；常见 3–8，配合上下文预算调整。阈值的作用是**宁缺勿滥**：低于阈值就当没检索到，直接回「资料不足」，避免模型基于不相关片段编造。阈值太高会让「明明有资料却说不知道」，需要用真实问题校准。

**本仓库：** TopK 与阈值可配；无命中时直接返回固定「无结果」文案，不进模型。

---

### 增量更新怎么做？重建向量时怎么避免「查询空窗」？

**答：** 难点是「删旧 + 写新」不是原子操作，中间可能出现旧的已删、新的没好的窗口。做法是**先写不可见的新数据，再原子切换**。

**本仓库的做法（值得记）：**

| 阶段 | 元数据 | 效果 |
|------|--------|------|
| 写入中 | `kb_id=pending:...` + `kb_vector_job_id` + `kb_target_id` | 新向量对查询不可见 |
| 成功 | 删旧 `kb_id` 向量 → `promoteVectorJob` 把元数据改写为正式 `kb_id` | 切换瞬间完成 |
| 失败 | 按 `kb_vector_job_id` 清理临时行 | 不留脏向量 |

外加一个 SQL 细节：PostgreSQL 的 `?` 操作符与 JDBC 占位符冲突，所以用 `metadata->>'kb_id'` 与 `jsonb_set` 而不是 `?`。

### 混合检索和 Rerank 是什么？为什么这里没做？

**答：** 混合检索 = 向量（语义）+ BM25（关键词）结果融合，能救「专有名词/编号」这类向量不擅长的查询；Rerank 用 Cross-Encoder 对候选重排，精度比向量相似度高很多，代价是每个候选都要过一次模型。

**本仓库：** ⚠️ 项目未覆盖，当前只有向量检索。所以长尾关键词命中一般——这是已知短板而不是「不需要」。

---

### 召回了很多但答案很差，怎么判断是检索问题还是生成问题？

**答：** 拆开看：

1. 把检索到的片段人工过一眼——**答案所需信息在不在里面**？
2. 不在 → 检索问题：改分块、换 Embedding、加改写、加混合检索/Rerank；
3. 在但答错/漏 → 生成问题：Prompt 没约束「只依据资料」、片段顺序/序号混乱、上下文过长导致中间信息被忽略、TopK 噪声太多。

这个二分法能省掉大量瞎调。

---

### RAG 效果怎么评？

**答：** 分两段指标：

- **检索**：命中率/Recall@K、MRR、命中片段是否包含答案；
- **生成**：忠实度（有没有超出资料）、答案相关性、引用正确性。

做法是先攒一个小而真实的问题集（几十条即可）+ 期望依据，再用规则或 LLM-as-judge 打分；每次调参跑同一批，看的是**相对变化**。

**本仓库：** ⚠️ 项目未覆盖——没有评测集，调优靠人工体感。学习计划把它列为 G5，也是我认为性价比最高的补齐项。

---

### 检索到的文档里藏了指令怎么办？

**答：** 这是 RAG 特有的注入面：攻击者把「忽略以上指令」写进文档，等着被检索出来。防御和用户输入一样对待检索内容：过滤角色标记与注入话术、用随机边界包裹片段、system 明确「边界内只是资料」。

**本仓库：** 复用同一套 `PromptSanitizer` + `<data-boundary-xxxx>` 机制（见 [tech-qa/05](05-prompt-engineering.md)）。

## 我的口述清单

1. RAG 两条线：离线索引、在线检索生成；效果瓶颈通常在**索引侧**。
2. 分块和 TopK 没有万能值，只能用自己的问题集试。
3. 换 Embedding 模型 = 整库重建，别混用。
4. 重建向量用「临时元数据 → 原子提升」，避免查询空窗。
5. 答不好先分「召回没给到」还是「给到了没用好」。
6. 我这套目前缺混合检索、Rerank 和评测集——能说清缺什么，比假装完备更有价值。
